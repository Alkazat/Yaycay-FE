# Yaycay Back-end - Handoff

**Repo:** `github.com/Alkazat/Yaycay-BE`
**Read `00-MODEL-CONTEXT.md` and `00-LANDSCAPE-ADDENDUM.md` first.**
BE is the hub and **owns the contract** (`@alkazat/contracts`, published to GitHub
Packages). FE, Admin and Website are clients. Writing rule: no em-dashes.

---

## Mission

Produce, store, secure, and serve every family's trip and the full holidaying
experience behind a stable, versioned contract: API, AI harness, MCP, Stripe,
webhooks, and the data model. Independently deployable; RLS-isolated; truthful
contract (an endpoint enters the contract when its handler ships).

## Scope

**In:** the HTTP API and contract; auth and isolated identity; the canonical
data model and RLS; the AI harness (our-AI chat + BYO-AI MCP + ingestion +
generation); Stripe Checkout sessions and webhook entitlement; Brevo sync;
retention/disposal jobs; the reward economy, packing, journal, progress, and
safety domains the addendum introduced.

**Out:** the customer PWA (FE); the marketing site (Website); the admin UI
(Admin, though BE exposes the admin-scoped API it consumes); card handling
(Stripe-hosted).

## Stack & conventions

- TypeScript, Node 20. Supabase: Postgres (RLS) + Auth (isolated) + Storage +
  Edge Functions. Migrations via the Supabase CLI. pgTAP for RLS tests.
- Contract is generated here: `openapi.yaml` (3.1) + generated TS types + JSON
  Schemas (`trip-content.schema.json`, MCP tool inputs). Semver; breaking change
  bumps major. Publish to GitHub Packages on a tagged release.
- `develop` -> staging, `main` -> production; full test suite blocks merge;
  smoke test on deploy.

## Auth & identity

- Supabase Auth: email magic link **plus a one-time 2FA code on every sign-in**;
  password reset requires a secondary email. `POST /auth/2fa/verify` is served.
- Identity is isolated from trip data. The gateway verifies the JWT signature;
  handlers require `aal === 'aal2'` (verified MFA) and read `sub`. **`role` is
  not a JWT claim** - it is resolved server-side from `identity.accounts.role`
  keyed by `user_id = sub`. Only `role = 'admin'` passes admin authorization.
- Social media is a connector, not a login.

## Data model (extends model-context section 4)

Existing tables: `accounts`, `child_profiles`, `trips`, `trip_content`,
`trip_progress`, `journal_entries`, `media`, `ai_jobs`, `connectors`, `prompts`,
`products`/`purchases`, `marketing_contacts`. **RLS mandatory on every table
holding customer data**, proven by pgTAP (account A can never read account B).

New / clarified tables the addendum requires:

| Table | Holds | Notes |
|---|---|---|
| `child_profiles` (extend) | per child: name, avatar, age, **mode** (`standard`/`little`/`explorer_plus`), interests, **dietary/medical flags incl. anaphylaxis** | medical flags are sensitive; minimise; parent-owned |
| `trip_progress` (clarify) | per `profile_id`: ticked activity ids, active mode | **key by stable `activity_id`, never label text**; one row-set per profile |
| `journal_entries` (extend) | per profile/day/activity: rich text, **mood**, **1-5 stars**, `media_ref[]`, ts, edited | per-profile ownership enforced by RLS; last-writer-wins on sync |
| `star_ledger` | per `profile_id`: star events (source = `game`/`challenge`), per-day idempotency key, running balance | configurable rate (e.g. `star_value` in `trip` or account settings) |
| `packing_lists` | per trip: sections + items per profile and a shared family list; tick state; CRUD patches/additions | print/reset are FE; BE stores canonical + edits |
| `booking_checklist` | per trip (grown-ups): items, group, **done state (persisted)**, due date | fixes the prototype's non-persisted checklist |

Mini-games and star challenges are **content**, not their own tables: they live
inside `trip_content` (per day) and are generated by the AI harness; only their
*completion/claim* state lives in `trip_progress` / `star_ledger`.

## Content model additions (`trip-content.schema.json`)

Keep the Holiday -> Days -> Moments -> Activities shape. Extend to carry what the
prototype rendered, all schema-validated on write (`PATCH /trips/:id/content`):

- `activity.variants`: `standard` | `little` | `explorer_plus` blocks (copy,
  read-aloud text, fact, quiz).
- `activity.challenge`: typed `quiz` | `spot` | `photo` | `challenge` with
  question and answer (answer never read aloud).
- `activity.facts[]`, `day.did_you_know`, `day.weather`, `day.hotel` / move
  badge, `activity.location { name, lat, lng, zoom }`, `activity.safety`
  (allergy callouts: avoid-list, cross-contamination, EpiPen note).
- `day.game`: `{ type: tap|colour|spot, theme, config }`.
- `day.star_challenge`: per child `{ question, answer }`, age-differentiated.
- `grownups`: per-day logistics `{ bookings[], costs[currency], transport[],
  tips[], allergy[] }`, accommodation phases, plus the booking checklist seed.

Every generated payload must validate before persist; reject on schema failure.

## AI harness

- Model-agnostic; model per task chosen in Admin and stored with the prompt
  version and the `ai_jobs` record. **Default for use-our-AI is Claude Sonnet.**
- Two planning paths, one backend: our-AI guardrailed chat
  (`POST /trips/:id/plan/chat`, SSE) and BYO-AI MCP.
- Generation tasks the harness must run (prompts owned by the AI-prompts thread,
  see `04-AI-PROMPTS-HANDOFF.md`): demo day; full trip content with per-mode
  variants; typed challenges; facts/did-you-know; per-child age-differentiated
  star challenges; per-day mini-game theme/config; per-profile + family packing
  lists; grown-ups logistics; and the allergy-safety layer. All emit
  schema-valid `trip_content` blocks.
- **Jobs are bounded:** ingestion capped at ~10 AI updates/day per trip; beyond
  that, queue or manual. Every job logged in `ai_jobs` (model + prompt version).

## Payments (Stripe)

- Checkout, one-off (plus the recurring data-keep token). Entitlement set by
  webhook -> `purchases`. Card data never touches our systems.
- Catalogue incl. `price_holiday_byo` ($59), `price_holiday_ai` ($129),
  `price_datakeep_annual` ($9/yr), `price_destination_addon`, `price_explorerplus`
  (unlocks Explorer+), **`price_photobook`** (the journal "export keepsake"
  becomes the photo-book product), `price_gift`.

## Safety, privacy & retention (build requirements)

- **Allergy/medical data is sensitive.** Minimise, encrypt at rest, RLS-isolate,
  and never expose across families. The AI must treat anaphylaxis guidance as
  safety-critical (see the prompts handoff guardrails); BE validates that any
  activity tagged with a known allergen carries a `safety` block before publish.
- Australian Privacy Principles in code: data minimisation, purpose limitation,
  access control in schema + API. Private media via short-lived signed URLs only.
- **Disposal by default:** trip data scheduled for deletion 12 months
  post-holiday unless a keep-token is bought; `retention_expires_at` on `trips`,
  `data_kept` derived.
- In transit TLS 1.3 + hybrid post-quantum; at rest AES-256; secrets server-side.

## Offline & sync support

- Serve trips in a shape the FE can cache. Accept journal/media writes that were
  captured offline: **last-writer-wins per `journal_entries` row**, media uploads
  resume. Idempotency keys on star claims and journal saves.

## Definition of done

The contract is published and the API deployed (staging + prod). A family can
sign up, buy either tier, plan (chat or BYO-AI), and the FE can render a correct
per-child/per-adult experience with stars, games, journal, packing and the
grown-ups guide, all RLS-isolated and allergy-safe, green on `main`, contract
pinned by consumers.

## Handshake

- Bump the contract per change; tag a release; publish to GitHub Packages so
  consumers can pin. Tell FE/Admin which endpoints went live (they gate on it).
- Never ship a breaking change without a major bump. A consumer's gap is a PR
  here, not a workaround there.
